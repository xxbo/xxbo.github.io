# MAP40 内存稳定性专项：第一批

## 已完成的变化

1. 寻路搜索状态共享紧凑的前驱边链；中间候选不复制完整路径数组。公开 `paths` API仍返回原来的完整路径，需求计算则只在读取目的地结果时展开。费用、换乘、方向、同成本候选顺序及原有121边边界均保留。
2. 每次需求计算的寻路树缓存采用LRU，最多24组，累计搜索分配权重预算60000；超预算的单组结果当次使用后释放。策略缓存最多1024项。淘汰只引起重算，不裁剪OD、路径备选或客流。权重为搜索接受状态的累计生成数，作为保守分配预算，非字节数；预算统计描述保留缓存，不含正在生成的工作树。
3. 需求Worker输入去除客流历史、资金流水、效果记录和日志；保留计算所需的城市、线网、车型、时刻与当前线路参数。接入预测后，出行定义由运行时持有，展示预测释放对它的冗余引用。
4. 自动/手动保存先进入背压队列：一项执行、一项待执行。待执行项只保留取最新状态的函数；请求合并完成后再创建快照、复制到编码线程并写数据库。导入文件在写入前等待该队列排空，维持顺序和最后成功存档保护。
5. 退出运营中心时终止闲置诊断Worker并清理回包定时器；预测更新时清理旧的渲染分析引用。现有已计算结果可用于下次打开的首次显示，后台线程按需重建。
6. 运行诊断增加内存与后台任务详情：最多48条轻量样本，五秒节流和操作边界采样。页面堆统计取决于浏览器支持，只涵盖当前页面JS，额外显示预测/实际出行组合数、保存并发和合并次数、寻路与策略缓存预算。

存档格式、需求总量、票价、满意度、财务公式和模拟步长保持原规则。游戏继续采用带目的地的乘客群组，而非为每个人创建场景节点。

## 可复现的测量

```sh
node scripts/benchmark_rail_memory.cjs
node --expose-gc --max-old-space-size=512 scripts/stress_rail_memory.cjs
node scripts/run_rail_tests.cjs
```

基准在独立Node进程运行前后实现，固定512MB旧生代预算，主动GC后测存活堆；进程峰值RSS另行列出。环境、分配器和GC时机会影响数字。

### 寻路缓存基准

14条线路、49个站点、36组起点/时间价值组合，保留各组候选寻路结果并展开全部目的地，路径边数校验和均为31692。

| 指标 | MAP39 | MAP40 |
| --- | ---: | ---: |
| 缓存存活堆增量（GC后） | 3.20MB | 0.96MB |
| 进程峰值RSS | 83.18MB | 82.73MB |
| 本机执行时间 | 337.4ms | 313.5ms |
| 最终缓存组数 | 36 | 12 |

存活缓存堆下降约70%。此数据是特定寻路缓存工作负载的测量；浏览器还包含地图图片、DOM、渲染资源和多个Worker，各部分需要分别观察。

### 连续运行压力场景

10条线路、25个换乘网格站、6000份预测出行组合，连续12个游戏小时，每小时完整重算、连续接入需求、导出JSON、解析并恢复运行存档，共12次。试验完成6044次旅程，生成6168人次；每轮均校验乘客守恒和存档恢复。

- GC后样本：首小时24.89MB，最高25.51MB，第12小时25.49MB。
- 进程峰值RSS：275.63MB。
- 第12小时在线76列，预测和运行出行组合均为6000。
- 本机执行时间约41.6秒；游戏时间与墙钟时间分开统计。

该场景验证反复重算和保存后存活对象趋稳；RSS同时反映短时分配和进程开销。后续扩展站数、路线分支和需求规模时，继续保留相同的精确性对照与内存观察。

## 回归与边界

MAP40测试冻结MAP39寻路实现，对照普通/快车/跨线/环线、多时间价值、首段约束、所有目的地及完整需求分配；另测Worker输入投影的计算结果一致、缓存权重/条目限制、遥测上限、1001次密集保存请求合并为两次串行执行、编码错误后最后成功存档保护、连续客流接入与存档恢复。

浏览器验收覆盖旧存档启动、后台预测更新、运营中心反复进入/离开、运行诊断、保存、导出、导入和恢复。真实玩家大线网崩溃前的峰值曲线仍是后续定位具体触发点的重要输入。

## Rust / WASM 边界

网页可加载静态 `.wasm` 和JS绑定，Rust核心可放在Web Worker中运行；主界面通过明确的数据接口发出操作并接收摘要/增量。本轮建立预算、数据投影、背压、精确性和压测基线，为后续用Rust/WASM替换计算热点提供边界。WASM也需要紧凑数据、分配预算和跨边界复制控制。
